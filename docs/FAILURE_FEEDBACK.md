## 0.14.46：MiniMax 联网搜索的有限重试

MiniMax 联网搜索收到 HTTP 502、503 或 504，且响应没有 `Retry-After` 时，最多重发一次原查询。两次请求复用同一请求槽、取消状态和累计网络 I/O 预算。首次响应关闭后重新检查当前会话和剩余预算，成功才发布搜索来源。该策略限于 MiniMax 读取网页结果的接口。限流、额度、凭证、业务错误、未收到 HTTP 响应的连接失败，以及查询规划、语音识别、播报和 Dot 工具请求均沿原路径收尾。[MiniMax 搜索参考实现](https://github.com/MiniMax-AI/MiniMax-Coding-Plan-MCP/blob/main/minimax_mcp/server.py) · [HTTP Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)

证书验证开启的本地 HTTPS 回归覆盖三种网关错误后成功、第二次仍失败、明确延期、其他状态和其他入口。另在首个响应关闭时注入预算耗尽、取消或会话过期，核对均未发送第二个请求。此候选尚未部署，测试没有调用真实提供方或操作 CC8。

## 0.14.15：MiniMax业务失败分类与严格状态检查（源码候选）

过去只按HTTP状态分类；`HTTP 200`携带非零`base_resp.status_code`时，虽然请求已经失败，界面仍可能只显示“服务或本机处理失败”，无法区分额度和凭证问题。另有部分非整数零值会通过旧成功判断。新候选在返回ASR文字、JSON或SSE事件前共用状态检查，并在MiniMax专属异常边界转换为原有固定类别，不改通用异常的猜测规则或协议。

依据2026-11-03核对的[MiniMax官方错误码](https://platform.minimax.cn/docs/api-reference/errorcode)，仅映射明确含义：

| 既有界面类别 | 业务码 |
| --- | --- |
| 请求超时 | 1001、2066 |
| 服务限流 | 1002、1041、1045、2045、2046、2047 |
| 凭证或服务权限不可用 | 1004、2042、2049、2057、2061、2068 |
| 服务额度不足 | 1008、2053、2056、2067 |

HTTP分类仍优先，显式内部分类保持；未知、参数或模型状态仍保留通用失败，不匹配`status_msg`。例如2062在不同接口有上下文差异，不直接猜成同一种原因。不会自动切模型、换音色、改套餐、重试工具或重发任务。

出现`base_resp`时必须为对象；出现`status_code`时必须为范围内的非负整数，拒绝布尔、浮点、字符串、空值、列表等。缺字段仍按既有兼容规则支持普通/分片响应；搜索结果继续要求明确的整数零状态。畸形状态不能释放同一响应中的文字、音频、来源或完成结果；异常只留固定信息及受限整数，不把提供方正文/凭证放入界面、任务或诊断。

自动回归包括十八个已核对业务码的ASR／JSON／SSE及JSON错误回落，畸形状态与包络、未知码、普通成功兼容、搜索明确状态，以及真实RecognitionWorker／MiniMaxBrain／ResponseWorker／MiniMaxVoice的失败和下一次显式请求恢复。ASR失败不派发任务；TTS在PCM后失败仍保留已完成工作。另用证书验证开启的真实loopback TLS，对四类错误×三入口×三次共36组检查收尾及随后成功请求；本地固定响应不冒充实际MiniMax云端故障。

这十项定向回归在5703ffb旧客户端上复现155处断言失败、零fixture error；修复后及根目录＋最小PATH运行均通过。完整本机installer23／host680（4项既有private opt-in skip）／tooling100／Java15和固定质量检查通过。当前0.14.13／APK0.9.7及其只读观察不变；本候选未部署，上述故障注入未开麦/拍照或调用真实模型，不据此关闭生产错误/权限完整矩阵或P0-06。


另对本候选做一次真实正常接口兼容检查：独立进程读取同一有效配置与既有凭证，原MiniMax音色合成固定公开短句（31579帧），仅在内存封装WAV后送ASR，规范化正文匹配，再完成一次公开关键词JSON搜索；共三次真实提供方调用，TTS／ASR／JSON分别约0.776／0.619／1.063秒。这是组件请求耗时，不是声学响应时延或一般识别准确率。TTS状态为整数零，ASR成功响应省略业务状态，符合保留的兼容路径与[官方ASR示例](https://platform.minimax.cn/docs/api-reference/speech-to-text)；搜索明确为整数零。请求槽全部清空，有效配置/文件摘要、原backend实例与停采状态保持；不保存音频/正文/搜索结果、不在CC8播放、不调用Dot或执行用户任务。私有`normal-provider-probe.json`保留数字证明；正常调用成功不等于真实云端故障验收。

## 0.14.9：域名解析等待也有界（源码候选，未部署）

在既有MiniMax每请求HTTPS适配器里增加有界解析等待，DNS及返回地址的TCP尝试共用一次connect_timeout截止时间，同时受剩余累计I/O预算限制；普通HTTP CONNECT代理的主机名也走这条路径。保留原主机名做SNI/证书验证、原socket选项及源地址设置，不修改系统DNS、全局socket函数或其他请求的连接池，不增加重试。

OS的getaddrinfo本身无法中断；等待方每至多50ms检查取消，并在截止时间结束。解析只在最多四个daemon worker中执行，无排队或跨请求DNS缓存；占满时明确失败，不无限创建线程。迟到的解析结果只能释放该worker容量，没有连接、回调或重新提交请求的能力。源绑定名称也先解析为数字地址，避免socket.bind再次阻塞解析。

Requests会把代理连接超时嵌套成ProxyError/MaxRetryError，现只沿已知结构包装最多八层判断类别，不匹配异常文字；普通连接错误和循环包装不会被猜成超时。正常播放/消费时间仍不计入网络I/O。这里约束的是Python MiniMax调用，不声称控制Dot的Rust网络栈、所有代理实现或强行终止OS解析。

新增真实loopback TLS回归覆盖ASR/JSON/SSE三入口DNS阻塞、解析期间取消、代理DNS超时，以及释放后正常三入口成功。三项回归在旧ecd2f4e的http_budget实现上复现5处断言失败、零fixture error；修复后通过。另覆盖容量耗尽/释放、迟到结果不连接、启动线程失败、解析异常/空值/超量、事先取消、多个地址共用截止、socket选项和绑定名称。没有外部模型请求、录音、摄像头或设备动作；当前0.14.8实机观察保持原进程，新候选尚未部署。另以真实子进程验证未完成的daemon解析不阻止退出。本机全套installer23／host636（4项私有录音显式跳过）／tooling100／Java15通过，Ruff/Java格式与七模块strict检查通过；从根目录、PATH=/usr/bin:/bin实际执行13项DNS/验证TLS/取消/CONNECT回归也通过。

## 行为

- ASR 失败：这句话不会交给大脑；检查服务后可再说一次。
- Dot / MiniMax 大脑失败：结果可能不完整，先在电脑端核对已执行步骤。错误不再被包装成普通成功回答，RAM-only 任务卡保留固定的失败指引。
- 本次工具审批已拒绝：需要审批的操作本次未执行，已执行步骤仍需核对；当前没有悬挂的待批准请求。到电脑端核对权限后重新发起，不自动批准或虚构恢复入口。
- TTS 失败：明确是语音合成失败，已收到的真实 Dot 完成回执保持完成。查看任务结果，避免重新交办同一任务。
- 设备播放错误或没有 play_done：取消旧音频、显示播放失败/未确认；发送完 PCM 不算播放完成。停止与字幕/音频代次保持一致。
- 旧代次迟到错误：不覆盖新请求的界面或重放旧内容。离线仍按既有规则停止采集，重连不自动开麦。

没有自动重试 ASR 上传、模型执行、工具写操作、摄像头或播报。健康/只读诊断仍由原有监督/采集周期有界查询；不将未知任务包装成“只读”后重试。任何可能有副作用的请求，恢复前先核对回执。提供方不会被静默切换。

## 边界与保密

OperationFailure 传递固定 stage/kind；Dot RPC 和 turn 的已知超时、断连、审批拒绝在发生处分类。MiniMax 三种真实 Transport 入口保留 requests Timeout / 连接错误类别，不再统一丢成未知网络错误。HTTP 429 / 402 / 401、403 分别归限流 / 额度 / 凭证权限；不猜 MiniMax 未核实的业务码，未知仍显示其他服务错误。

流式 TTS 的下一块 PCM 失败仍属于 TTS，不因前一块 PCM 已播放而误标播放失败。任务回执和播报结果独立；取消音频不撤销已完成工作。错误 UI、任务恢复说明和日志不拼接异常正文、服务响应、密钥、地址或识别内容。

Dot turn 截止时间和播放 ACK 截止时间保持。MiniMax 的累计网络预算补充见下文；恢复状态仍需实际请求证明。

## 0.14.3：慢速响应的累计网络预算（软件候选，未部署）

Requests 的 read_timeout 只限制一次读取。服务每隔一小段时间返回几个字节，可让响应头、JSON 或 SSE 持续拖延，即使每次读取都没超时。现在每个 MiniMax ASR / JSON / SSE 请求独立累计连接与 socket 读写耗时，预算为现有 connect_timeout + read_timeout（默认8+20=28秒），每次实际 socket 操作的等待上限同时受剩余预算约束；不增加重试、不改服务或凭证。

预算经过 HTTP 缓冲解析器生效，涵盖响应头、正文、chunk framing 和普通 HTTP 代理 CONNECT。池类映射按请求复制，保持证书/主机名验证与已有代理配置；不修改 urllib3 全局池映射。当前 Requests/urllib3/Python 固定版本已做真实 TLS 回归；没有声称未测网络栈或所有代理实现都兼容。

正常播报、暂停和消费已返回事件的时间不算网络等待，避免长回答仅因播放较慢而失败。它是累计网络 I/O 预算，**不是整段对话的墙钟上限**；当时系统 DNS 解析不能在此处中断，返回后才计入连接耗时；0.14.9源码候选另补有界等待，OS调用本身仍不能强制中断。没有将该补充当作完整 P0-06 验收。

取消先只 shutdown 当前请求拥有的 socket，唤醒响应头或正文阻塞读取，再沿既有异步关闭路径收尾；重复取消不再持续创建关闭线程。TLS-in-TLS 包装本身没有 shutdown，取消沿它的已拥有底层 socket 执行；该分支有固定版本结构回归，不冒充完整 HTTPS 代理实测。旧请求不能关闭后来的独立请求。Requests 将流式读取超时包装成 ConnectionError 时，也归为 timeout，保留现有分阶段失败指引和已完成任务结果。

自动测试使用临时证书、证书验证开启的 loopback TLS 服务：修正为完整消费请求体的 fixture 在旧 bfb6388 实现上复现5处预期失败、零 fixture error；修复后响应头/JSON/SSE/CONNECT 滴流均按预算结束。另有正常三入口、成功 CONNECT 后的 TLS/JSON、取消阻塞头/正文读取、错误主机名拒绝、缓冲 makefile、嵌套不重复记账、消费者时间不计费、请求/代理池隔离和重复取消回归。不联系模型服务、不启停设备或开麦。

## 0.14.4 / APK0.9.1：错误不再被收尾覆盖（软件候选，未部署）

自动检查发现，麦克风关闭时的TextReply失败先执行finish_text，清掉唯一有效owner，再进入外层错误处理；valid已为false，因而只有正常text_done，没有错误提示。现在串行worker在owner仍有效时先发布分类错误，随后才清理文字会话。错误发布与新请求准入共用已有session锁；ASR与指定播报的同类失败发布也采用这一边界。清理通知发生连接错误时仅记固定异常类型，worker继续处理后续请求，不重试已执行任务。

设备端原先无条件用“任务已结束/播报未完成”替换错误。现在StatusFeedback只保存代次/终态标志，不保存内容；结束回执仍释放播放控件，但保留同请求的错误及恢复说明。状态必须属于前台当前请求，低于取消边界或已知最新代次的状态不能覆盖新请求；旧text/announcement结束回执也不能关闭较新的控件。切换连接或显式开始新麦克风时重置这份状态。

播放失败会先cancel输出，再报告原因。只有设备刚刚拥有该取消请求时，才接收对应代次的一条终态错误；无任务的被动取消不授权任意错误，重复取消不隐藏已经显示的错误。实际协议的cancel(N)→text_begin/announcement_begin(N)仍允许第一次合法begin；重复begin不能重开失败请求。正常多句播报和下一次成功请求仍正常收尾。
