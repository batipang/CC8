# 任务结案与停止时的清理归属

后台 0.15.52 候选修复三个关联边界，服务、Provider 和回答线程一起验证。默认 MiniMax ASR/TTS、Dot、原 APK 0.9.47／code84、协议和采集规则保持。

## 回答任务的终态

回答线程迭代 Provider 时已经拥有任务、主错误与诊断记录。原来显式关闭迭代器若抛错，会跳过随后任务结案，留下 running 任务；也可能让次要清理错误取代已经发生的播报错误。

现在关闭迭代器的异常只记录固定事件及错误类型，继续在原会话锁内完成收尾。原始 TTS 分类与恢复指引保持；已完成的 Dot 任务继续完成，取消朗读不撤销工作。主迭代阶段本身抛出的异常仍是正常失败，不被清理容错掩盖。不重试请求、不换 Provider、不保留声音或错误正文。

## 独立资源均尝试关闭

`cleanup_all` 顺序调用已拥有资源的清理动作，即使某个动作抛出普通异常，也继续其余动作，最后重新抛出第一个异常；后续错误不替换主原因。它不重试、不创建新资源，不把尝试关闭等同于成功关闭。

- BrainRouter 会尝试 MiniMax 与 Dot 的取消；关闭路由器时，无论取消结果如何，仍尝试关闭 Dot。
- DotBrain 即使不能启动中断线程，也会关闭自有 RPC / 守护生命周期。
- 实际注册的 SIGTERM / SIGINT 处理先设置停止标志，再尝试停会话、停止输出、失效播报、取消回答、关闭 IPC、传输、脑、语音请求及当前连接。连接 shutdown 失败仍会尝试 close。
- 原有取消和连接的预期断管 / OSError 处理保持。其他操作异常会在所有独立动作之后传播，不能据此宣称资源必然释放。

## 验证范围

八项新回归覆盖任务错误终态、已完成结果、取消、双 Provider 失败顺序、十种停止阶段异常、三个预期 I/O 分支，以及真实本地 stdio RPC 的取消线程启动失败。最后一项使用无模型、无工具执行的测试服务器，确认自有守护进程退出、生命周期 socket 关闭；没有访问实际 Dot 模型或设备采集。

完全相同的最终测试在原版 `c24e3c6` 得到六处断言失败、零 fixture error；新版八项通过。最初测试服务器缺少 initialize 应答、将守护 socket 当作进程的夹具错误分别保留，修正后才运行上述配对，不计作产品回归。相关调用链 66 项检查也通过。完整回归 / CI 和运行实例维护分开记录；这不代替真实登录、系统睡眠、任意工具树或 72 小时验收。
