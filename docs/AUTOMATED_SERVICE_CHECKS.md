# 自动后台崩溃恢复检查

P0-02 的真实进程验证使用 `verify-service`，与隔离模拟 worker 的 supervisor 单元回归分别记录。默认只打印计划，不查设备/进程、不创建目录、不加载模型。

```sh
./cc8 verify-service --runtime-root /absolute/live/workspace
# 最多十轮；显式终止空闲的本项目后台，由已有守护恢复
/usr/bin/python3 cc8 verify-service --runtime-root /absolute/live/workspace --cycles 10 --execute
# 独立验证 launchd 替换监督进程；不终止语音后台或重新提交任务
/usr/bin/python3 cc8 verify-service --runtime-root /absolute/live/workspace --fault supervisor --cycles 1 --execute
```

执行前须由用户授权相关维护，实际运行目录必须是已启用原有 LaunchAgent 的真实绝对路径。共享实际 runtime 的 `automation-test.lock`，不能与自动设备测试并行。不会安装/启用一个停止的服务，不调用任意终端命令，不打开 UI、不开始麦克风或相机。

## Mac 睡眠与恢复观察

```sh
./cc8 verify-service --runtime-root /absolute/live/workspace --observe-sleep
./cc8 verify-service --runtime-root /absolute/live/workspace --observe-sleep --sleep-wait 900 --execute
```

第一条仅显示计划。执行模式等待一次外部发生的系统睡眠，使用同一把自动验收锁。它不发送睡眠命令、不阻止睡眠、不重启服务、不打开助手。等待预算按 Mac 清醒时钟计时，睡眠持续时间不占用预算。相邻两次采样之间，连续时钟比清醒时钟多走至少 5 秒才记录睡眠证据。分散在不同采样间隔内的短暂停不会累计。普通调度延迟和系统墙钟变化不满足条件。 [Apple 时钟说明](https://developer.apple.com/documentation/kernel/1646199-mach_continuous_time)

系统 Python 3.9 与开发环境 Python 3.13 均拒绝同时指定 `--observe-sleep` 和 `--fault`，包括显式指定默认值 `--fault backend`。省略模式参数时默认选择后台故障检查。

睡眠前与恢复时都核对已绑定的 ADB 传输与 Mac USB 注册树的设备序列。唤醒后先复核同一设备和端口，再查询原 LaunchAgent、原后台实例、CC8 前台及 USB 就绪。每份就绪结果须来自同一次 USB 枚举。同一设备在原端口重新枚举时，丢弃该次结果并等待下一次完整采样。任一观测点发现设备或端口变化，即停止验收。ADB 暂不可用时也会复核身份。该检查需要后台 0.14.44 起提供的累计音频计数。两端必须停采，帧计数、自动开麦次数和请求集合保持原样，再观察 3 秒确认稳定。报告保留睡眠时长下界、恢复首次可见时间和未就绪采样次数，不保存设备序列、进程号、实例或请求 ID。若首次查询已经就绪，报告表示睡眠后已恢复可用，连接在睡眠期间是否曾断开仍未知。

离线回归覆盖超过等待预算的睡眠、分散在多个采样间隔的短暂停、USB 就绪查询期间重新枚举以及恢复超时。本机双时钟只读检查在无睡眠时仍以未观察到睡眠退出。实机系统睡眠需在 72 小时长稳观察之外另行验证。

## 门控和依据

- 正常 Android 模式下唯一 AILABS_S6 / SDK27 / shell UID2000，每次状态操作重核同一 USB target。
- 用户自己的服务启用标志和 LaunchAgent 必须匹配该 runtime；进程列表按 UID、完整脚本路径和参数核对，一个 supervisor、至多一个 backend，额外参数的同脚本进程也拒绝。后台通常是对应 supervisor 的直接子进程。service.py已有接管存活后台的逻辑；若父PID为1，还必须有六秒内的私有ready回执，以及launchctl对同一LaunchAgent当前监督PID的确认，后台PID仍须与ready回执匹配。其他父进程拒绝；仅有PID文件或名字包含bridge不作为选取依据。
- 源码/backend/protocol/APK 版本相符；设备前台、双端麦克风关闭、摄像头关闭、无播放/校准；有未完成的诊断请求就拒绝。每轮发信号前再次核对完整空闲快照、实例与进程，不跟随更换的目标。
- 默认`--fault backend`只向核实的本项目后台PID发送一次SIGKILL。显式`--fault supervisor`则只向同一LaunchAgent核实的监督PID发送一次SIGKILL，不向后台发信号。两者都不操作OEM服务、其他工作区或系统分区，不调整守护退避。
- 恢复须同时观察新 PID 和新 runtime instance、worker/model 就绪、USB 连接、supervisor ready、双端仍不开麦；三秒后重新核对稳定快照，再计本轮通过。每次等待上限90秒。
- 监督故障模式要求新的监督PID，并确认故障之后写入的新ready回执；可以接管相同后台PID/实例，也可以恢复为全新的后台PID/实例，不能只换其中一个。两个进程快照之间恰好出现替代监督时，下轮重新核对全部门控，不能直接算成功或误报重复服务。任何实际重复服务仍立即失败。

这是用户级空闲后台的故障注入；不是睡眠/登录、任务执行中崩溃、真实物理 USB 拔插或副作用任务不重跑的完整验收。进程身份核对与信号调用是独立系统调用，不能宣称提供 macOS 不具备的原子 PID 句柄保证。遇到所有者开始使用设备或停止服务即中断，不覆盖用户操作。

## Dot 同组工具的关闭

2026-11-04，0.14.26 候选修复隔离 app-server 关闭时的进程组清理。旧版只等待主进程退出，忽略 SIGTERM 的同组工具可能继续运行。主进程已退出时，旧版的 liveness 检查也可能先回收主进程 PID，使后续关闭跳过该组。

新版以不回收 PID 的方式检查 app-server，关闭和启动串行，已关闭客户端拒绝再启动。关闭先通知本客户端等待的请求，再向其启动时建立的独立进程组发送 SIGTERM。两秒内轮询同组成员状态，必要时发送 SIGKILL，并短暂确认退出后回收主进程。组信号只使用该客户端创建、仍由该客户端保留 PID 的组。

回归通过真实本地 stdio 初始化，覆盖合作退出、主进程退出后仍有同组工具忽略 SIGTERM，以及工具继续持有 stdout 时主进程已自行退出。关闭后再启动也被拒绝。测试只使用隔离脚本和临时目录。该路径适用于后台仍能执行关闭的场景，后台自身 SIGKILL 和工具主动脱离进程组需要各自的验收。

## Dot 后台异常退出时的守护

0.14.27 候选为每个 Dot RPC 客户端启动一个独立的本机守护。守护启动和回收自己的 app-server，沿用两秒进程组关闭期限。后台和守护通过私有 Unix socketpair 感知对端关闭。后台被 SIGKILL 时，内核关闭仅由它持有的端点，守护在另一端检测到 EOF 后清理自有进程组。app-server 自行退出时，守护也会清理同组工具。

原 JSON-RPC 管道由后台和 app-server 直接持有。守护启动后释放自己的管道引用，使用单独的状态通道标记不可用。stdout 读取器仍按顺序处理缓冲中的终态回执。后台正常关闭时先释放状态通道，再有界等待守护退出。

隔离回归使用实际启动入口、真实 stdio 和临时工具进程。它核对测试后台被 SIGKILL，以及 app-server 写出完成结果后退出、同组工具继续持有 stdout 两种异常。两种都要求工具和守护自行退出。旧版在这两处断言失败，候选通过。另用本机真实 app-server 在最小 PATH 下验证初始化和正常关闭，分别耗时 0.309 秒和 0.086 秒，全程没有提交任务。守护自身被强杀、工具另建会话、真实 Mac 登录及现场恢复仍有独立验收范围。

## 注册失败后的状态恢复

0.14.29 在写入配置前检查当前用户的 launchd 域，并保存先前的私有配置和启用标记。配置文件以原子替换写入，安装、停用和卸载共用同一份本地锁。注册或启动失败时恢复先前文件。若本次尝试注册了新任务，只有 launchd 回报的配置路径与本地配置匹配，才卸载该任务。已有任务保留，无法确认回退时明确报告。

定向回归覆盖域不可用、注册失败、注册超时但任务已加载、新任务启动失败、已有任务启动失败，以及安装与停用竞争。旧版六处断言失败，候选通过。实际 launchd 隔离验证中，首次安装成功到达 ready，新注册后的启动失败回退了文件并卸载任务，已有任务的启动失败逐字节恢复文件并保留原注册。所有临时任务均已清理。这些验证使用独立标识和合成后台。

## 手动启动与登录监督共用启动锁

后台 0.14.32 候选让手动启动和登录监督共用工作区的 `launcher.lock`。监督在锁内核对存活 PID，启动成功后在释放锁前原子发布 PID。手动启动可复用正在加载模型的后台，状态仍由健康接口判断。现有全局运行锁继续限制不同工作区。监督等待锁期间可响应停止，抢到锁后会重新核对启用状态。

两个本机进程用例覆盖两种启动顺序。旧代码两项断言均失败，候选通过。另在当前用户域加载独立的临时 LaunchAgent，让合成后台阻塞在就绪前。实际执行手动启动在 0.508 秒内复用原 PID，未创建第二个进程。解除阻塞后，登录任务正常达到 ready，监督崩溃后的接管、后台崩溃后的恢复和停用测试也通过。临时进程和任务均已清理。该测试未修改现场服务、未连接设备，也未触发系统登录或睡眠。
