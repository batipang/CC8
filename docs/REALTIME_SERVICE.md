# 实时语音服务的资源策略与恢复提示

0.15.67 候选关联 P0-01 / P0-02 / P0-03 / P0-06：修正常驻语音服务的 macOS 资源分类，并让可选英文复核的恢复／失败状态进入已有可恢复错误提示。APK、正式 MiniMax ASR／TTS、owner Dot、模型与采集门槛保持。

## 实际发现

0.15.66 已部署但英文增强原先关闭。固定四项现场计划按“原模式近音词、原模式正确词、增强模式近音词、增强模式正确词”执行：原模式的 `Humble bee` 未唤醒，`Bumblebee.` 唤醒并完成一次识别；第三项在外部试音前因英文模型未就绪停止，第四项未执行。不能把这轮写成英文增强通过。

之后两次仅观察启动、不播放外部试音的有界诊断均看到：中文模型就绪，英文模型经历三次启动、退避后进入失败。第二次对确切参数、用户与 Bridge 父进程均已核对的英文子进程采样一秒调用栈，观察到 Python 导入工作。每轮均停采并恢复原配置，最终独立检查确认原 APK、profile、LaunchAgent 和 owner 配置保持，前台 USB 优先、Wi-Fi 就绪、麦克风／相机／播放／校准关闭及模型进程退出。

同一实际运行解释器、固定代码和缓存的隔离模型启动对照，不访问设备、不输入音频：

| 进程策略 | 中文模型 | 英文模型 |
| --- | --- | --- |
| 普通终端 | 0.7214 秒就绪 | 2.1629 秒就绪 |
| `taskpolicy -b`，子进程继承 Darwin background | 2.8770 秒就绪 | 五秒内未就绪，由原适配器回收 |
| `taskpolicy -a`，应用资源策略 | 0.6213 秒就绪 | 2.2248 秒就绪 |

所有隔离子进程均确认退出。这里的次数少且没有端到端语音输入，是资源策略定位，不能写成整体性能或真人召回率。

## 候选修正

原 LaunchAgent 的 `ProcessType=Background` 用于未由用户直接请求的后台工作。本服务处理明确开启的交互语音，且子模型有严格启动和解码期限；新生成的 LaunchAgent 改为 `Interactive`。沿用 socket／管道通信，没有可用的 XPC 事务用于 `Adaptive` 切换。[Apple 的 launchd 手册](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5)解释各资源分类；本机 `man launchd.plist` 与 `man taskpolicy` 另核对了当前系统行为和子进程继承。

不提高模型期限、重试预算或声学门槛，不增加忙等待、保活锁或防睡眠。已有 LaunchAgent 只在显式维护重启时更新，不能仅合入代码就声称运行实例已改变。需要受保护 CI、维护部署及实际服务对照后才判断现场修复。

等待唤醒的当前有效收音帧检查两种模型的恢复快照。中文复核的故障优先展示；中文就绪不能清除仍未恢复的英文增强错误。英文增强失败时明确说明基础英文唤醒仍可用，保留原八路判断。全部有效模型就绪后恢复普通等待提示。同一状态不逐帧重发，正在播报／忙碌／已唤醒／旧代次时不覆盖当前反馈。健康查询不会启动、轮询或恢复模型。

## 验证范围

新增回归在原代码上为五项中三项断言失败、零 fixture 错误；覆盖错误被隐藏、中文先就绪误清除英文错误，以及生成的服务策略。候选定向五十项通过，完整 host 1716项通过（四项既有私人录音 opt-in 未启用）、工具158项通过；409个 Python 文件格式／静态检查、14个严格类型模块及既有 Java 格式通过。精简 PATH 下的真实配置序列化通过，未注册或启动服务。受保护 CI 和维护后现场结果分别记录，未完成的阶段不预先计为通过。

英文增强保持未正式采用。修正启动不等于证明新增候选有效；后续仍要求实际正确词和近音词都走到新增确认路径，并检查停止后的资源释放。真人、远场、电视和最终 72 小时验收继续分别保留，72 小时仍排在全清单最后。
