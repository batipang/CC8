# P0：播放时钟的生命周期对照与后续实现

2026-11-05，生产已升级为后台 0.14.85／原签名 APK 0.9.37（code74），源码 `4f660f6`。升级前的隔离对照只安装和移除独立输出测试包，没有采集声音、图像；升级后另外执行了显式限时实机录放检查，结果分列于文末。功能排期仍在 [统一 TODO](TODO.md) 的 P0-01／P0-04；本页保存实验依据与实现约束，不增加第二份待办。

## 实际设备对照

隔离包复用当前源码的 `PlaybackClock` 和 `RenderClockStats`，配置与生产一致的 16 kHz、单声道 PCM16、STREAM_MUSIC、缓冲下限和 0.35 轨道音量。APK 经实际清单检查不含任何权限，不使用麦克风、相机或网络。每轮写入 60 个 320 帧块，以低音量短音和尾部零样本检查时钟与播放头；播放头确实越过短音末尾才收录结果。

首次对照依次执行三组，各六轮：每轮新建并直接写入内容、每轮新建并先写入 9600 个零样本、同一 AudioTrack 跨六段保持零样本间隔。9600 个样本对应 600 毫秒音频，不等于测得的初始化墙钟耗时。随后按预先固定的冷／热／热／冷顺序重复三次，共十二轮，使用不同的短音。验证前约定：六轮热启动均无超过 40 毫秒的步长，最大步长不超过 2 毫秒，并与交错冷启动控制比较。

| 条件 | 轮数 | 出现超过 40 毫秒步长的轮数 | 各轮最大步长的范围 | 应用写缓冲欠载次数合计 |
| --- | --- | --- | --- | --- |
| 新建后直接写内容，含交错控制 | 12 | 12 | 64.038～107.747 毫秒 | 2 |
| 前置零样本，含交错验证 | 12 | 0 | 0.031～0.085 毫秒 | 0 |
| 持续播放时钟，首轮前置零样本 | 6 | 0 | 0.041～0.080 毫秒 | 0 |

两轮执行分别为 69.871 秒和 59.752 秒，测试包均核对摘要后移除，原助手不开麦恢复前台，同一生产后台继续工作。独立复核绑定了原始报告、实际编译 Java 来源、全部 18＋12 个数值结果及预定交错规则。报告摘要分别为 `c55b58e1c49304782aa15c9627c2385f539c01cc8e63a0650ac565b1f3df3ab9`、`1340bec602475d458be0a63bfaf2c7301da2b1dba6006f0eb30939c3b3a1a07d`；原始报告和研究脚本留在本机忽略目录 `speaker-clock-lifetime-20261105`，尚不是通用项目命令。

在当前设备与固定输入上，轨道初始化方式对应不同的呈现时间估算稳定性。冷启动共记录 17 个超过 40 毫秒的步长及 2 次应用缓冲欠载，尚未测量两者的逐项关系，不能把每次跳变都解释为欠载。这仍是数字时钟／播放头证据，没有测量扬声器首声、AEC 效果或一般语音准确率，也没有解释录音 API 的帧位置越界。

## 输出资源组件与接入约束

独立的 `SpeakerSession` 资源组件在 PR #241 合入；APK 0.9.37／code74 经 PR #242 将 `VoiceSession.Player` 接入该组件并已原签名部署。组件通过 `Device`／`Factory` 接口隔离 Android；一个输出线程初始化轨道、按实际接受的零样本建立时钟，并在无租约期间维持输出。等待租约的调用方在预热完成后取得写入优先权，交接先等待正在进行的写入完成计数。每句租约绑定 generation、playback ID、物理帧起点与资源代次，逐句播放头不计入前置零样本。

正常完成只交还租约；暂停保留租约且不写入空闲零样本；取消先作废租约并同步暂停、清空，输出线程等待迟到写入返回后再次清空，再开始新代次。关闭不会在原生写入尚未返回时释放轨道，也不会让阻塞的构造在生命周期结束后开始播放。原生写入、控制或初始化失败会关闭该组件，后续申请不能悄悄重用失败资源。播放头的低 32 位按已接受的物理累计帧展开。

离线测试直接编译并运行生产组件及 Java 线程夹具，覆盖句间复用、本句播放头、迟到写入的双次清理、暂停恢复、构造中关闭／失去所有权、阻塞内容及空闲写入时关闭、原生负值／超量／异常／零写与短写、控制失败、等待方撤销、原生初始化与空闲写入失败，以及低 32 位回绕。控制失败发生在另一个线程阻塞写入时，也必须等写入真正结束后再释放。该测试不访问 Android、设备音频或云服务，不能证明实际时钟稳定性或声学表现。

基础组件批次验证：23 项组件线程测试通过；全仓离线安装器 23、主机 1110、工具 129、音频 Java 15 项检查通过，其中主机的 4 项私人录音测试按既有显式授权规则跳过。静态／格式检查及 assistant 的 Android release Java 编译、lint 通过。另在临时源码副本分别移除第二次清空、错误地提前清除在途写入标记，两种错误均被对应线程回归拒绝；没有将这些负向副本写回候选或运行设备。

播放器由会话级输出组件拥有唯一 AudioTrack 和空闲零样本写线程，逐句 Player 只取得绑定 generation／playback ID 的租约。轨道初始化期间建立时钟，语音会话内跨句维持；不在每句话前固定插入一段静音。字幕、嘴型和进度只看本句实际内容，不把空闲零样本算作已经播出的内容。

Android 的 [AudioTrack 时间戳说明](https://developer.android.com/reference/android/media/AudioTrack#getTimestamp(android.media.AudioTimestamp))区分初始稳定期与稳定运行后的低频查询，并建议在应用层构建高分辨率映射。后续组件需要分开物理累计帧、本句起点与内容帧，处理播放头的 32 位回绕；不能直接把轨道累计播放头送给现有逐句回执。协议 2、原音色、配置、权限和 MiniMax／Dot 分工保持。

| 边界 | 必须保留的行为 |
| --- | --- |
| 内容写入与空闲维持 | 同一时刻只有一个写者。租约交接等待在途零样本写入入账，旧线程不能写入或关闭新租约 |
| 正常句尾 | 确认内容末尾已播放后交还租约；后续零样本不推进旧字幕，也不改变已完成任务 |
| 临时插话暂停 | 暂停与恢复回执、参考时间线及冻结画面仍对应同一租约；暂停期间不启动空闲写者 |
| 确认取消 | 作废旧租约，暂停并清理旧排队声音；只在清理完成后重建物理计数与时钟锚点，迟到清理不影响新回答 |
| 手动停止、后台、两路全断 | 关闭空闲维持、取消在途写入并释放轨道；重连不能自行创建输出资源或开启采集 |
| 独立播报／看图回答 | 只在现有明确授权及前台生命周期内持有输出资源，结束后释放；桌面入口服务不持有音频资源 |

## APK 0.9.37 接入实现

`SpeakerOwner` 只在明确的语音开始或独立文字／播报／看图回答请求开始时建立输出所有权。持续语音绑定本次录音 epoch，独立任务绑定 generation；前台状态、原请求状态和所有权票据均须有效。单纯 `play_begin` 或 PCM 不能创建输出。手动停止、后台及两路全断会关闭组件；旧录音线程的收尾和旧任务完成只结束其自身票据，不关闭新任务。仅向桌面返回照片的请求不建立音频输出。

`NativeSpeaker` 保留原配置与 0.35 音量，检查初始化和音量设置失败时释放已创建的轨道。API 23 以上使用有版本保护的非阻塞写入，每次最多 320 帧；旧 API 保留有限块写入路径，短写／零写由原有 `PcmPump` 处理。Android 的 [写入接口与播放头说明](https://developer.android.com/reference/android/media/AudioTrack)明确区分返回的实际写入量与已播放位置；这些 API 规则不证明当前硬件的声学效果。

Player 用本句起点加已写内容帧投影硬件时间戳，输出参考与诊断的帧号仍从本句零开始；排空填充只推进物理计数。字幕、嘴型、首次播放回执和完成帧数均使用本句播放头。轨道还在播放正文之前的零样本时，本句播放头为 0，嘴型保持静止；不能仅凭轨道处于 PLAYING 状态就打开嘴巴。该边界在前一候选上可复现，加入正文播放头前进的条件后通过。完成回执发布前先交还租约，因此下一句即使早于旧线程的 finally 到达，也不会触发旧线程释放或重置新轨道。

接入审查同时修复旧连接消息的竞态：控制解析后、发布前在连接锁内再次核对原连接代次，Player 及其 PCM 也绑定该代次。原主分支可以通过真实线程屏障复现“解析期间切换连接后，旧 announcement_begin 仍设置播报状态”；候选拒绝该消息。离线夹具编译完整的实际 Player、原生适配器、资源组件及生命周期辅助方法，保留原暂停／恢复／失败回执与嘴型冻结断言，并覆盖新句先于旧 finally、停止后迟到 PCM、独立任务收尾、物理／本句帧计数、原生初始化失败及旧 API 路径。

CI 另发现显式停止回执的竞态：若先标记 Player 停止，输出线程可先观察到失效并清理租约，使显式取消拿不到已应用的原生回执。修正为先作废租约、同步暂停和清空并记录时间，再发布停止标记及中断 Player。新增派生线程夹具只在停止标记写入后插入原生重置的 latch 检查点，保持原生控制及回执代码；旧候选 `901fe29` 得到预期失败，新顺序通过。检查同时持有现有连接／会话锁，输出线程仍须独立完成清理。普通夹具继续编译未插入检查点的完整实际 Player。

接入批次本地验证：新增 14 项接入测试和 1 项旧连接控制解析回归；原暂停测试迁到同一套完整 Player 夹具，保留原验证的行为并适配共享轨道的清理次数。全仓安装器 23、主机 1125（4 项私人音频按规则跳过）、工具 129、音频 Java 15 项检查通过；固定版本的质量检查和 APK0.9.37 的 release Java 编译／lint 通过。旧连接竞态在原主分支 `734a02c` 上得到预期失败、候选通过；这些结果均为离线证据。

## 验收范围

先用真实线程验证租约交接、初始化中取消、阻塞或短写中的停止、迟到释放、暂停恢复和计数回绕，再执行原有 Java／主机回归与编译、lint。实机分别复核时钟来源、同回合多段播报、字幕嘴型、普通音量新问题插话、无人交办时无新回合及关麦收尾。同步修正不能只靠这三十个时钟结果关闭 P0-04。

原签名升级后，冻结 `4f660f6` 的基础检查九项通过，492 次硬件时钟观测没有超过 40 毫秒的步长，最大步长 0.111462 毫秒；第二轮 535 次观测同样没有大步长、最大 0.087231 毫秒。但第二轮严格起始声学检查失败，新问题插话的第三轮也因可信人声／播放参考重叠未确认而失败。第三轮原播报取消、新回答完成，VAD 有声起点至设备暂停回执 253.2 毫秒；不据此判定严格插话通过。三轮都确认收尾关麦，完整数据与失败范围见 [当前部署](CURRENT_DEPLOYMENT.md#01485code74-自动验收)。

仍须测量逐句起播与总响应时延，确认没有每句额外静音，并记录前台空闲维持时的 CPU、内存及线程；后台和手动停止后不得继续写音频。持续复用不能保证网络慢包期间也完全不会欠载，保留原失败报告并继续验证参考重叠与声音表现。正式 72 小时观察仍留到功能稳定后。
