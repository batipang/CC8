# 后台输出的线路归属（P0-05）

后台 0.15.49／APK 0.9.47（code84）已部署。九项维护检查与双端新封套版本复核通过，后续同版硬件空闲往返、录音组合及播报断链结果见[部署记录](CURRENT_DEPLOYMENT.md#01549code84-双向线路隔离与自动检查)。本改动继续补齐 0.15.48 的设备→Mac 隔离，为 Mac→设备的控制和音频增加逐激活归属。

## 复现与修复

原设备控制入口在同一 Link 重新激活后，可能将此时才首次解析的旧 `announcement_begin` 归给当前路由。回归现编译生产路由／分派方法、实际 StatusFeedback、SpeakerOwner 和 SpeakerSession，仅替换平台接口与音频设备；旧代码有一个断言失败，零 fixture 错误。修复后旧事件不能取得输出资格，当前封套可以建立真实软件播放租约并写入一个内存合成采样。该证据不代表现场已发生重播，也不是物理扬声器测试。

设备继续声明 `route_envelope_version=1`，另声明整数 `route_output_version=1`。后台只在双方均支持时启用输出封套，并在 `transport_activate` 回传输出能力、本次随机标记、进程标识 `route_owner` 和递增 `route_serial`。标记仍使用类型 6，包头和原载荷预算保持；旧端仍保留原协议 2 的兼容路径，但不能据此验收双向隔离。

设备同时保存原路由号、标记和协商模式，再解码消息；解析结束仍核对原路由。旧标记、双向模式下未封装的应用消息、失效来源和迟到解析均被拒绝。配置局域网的 `lan_config` 同样封装，不能借连接管理入口绕过应用归属。`transport_ping`、`transport_activate` 和 `transport_standby` 保留管理通道，封套中的同名应用事件不能改变角色。

## 激活顺序和后台重启

后台进程使用新的随机进程标识，所有线路共享递增序号；失败尝试也消耗序号，不重复使用。设备在原路由锁内拒绝同进程的旧序号和重复序号，避免跨线路迟到的激活覆盖最新角色。后台重启可从新标识和小序号开始，应用回答代次也可重新开始；最近 16 个退役进程标识只保留有界元数据。来源仍须通过原连接、前台和生命周期检查，旧连接按原流程关闭，不以此替代 USB 验证、TLS 或配对认证。

## 发送和恢复边界

后台输出在等待写锁之前绑定原连接与标记，写出时复核；已经封装的旧消息不能改标后发给新线路。SPEAKER 仍核对回答代次，已知过期的 PCM 在编码前丢弃。设备解码和 JSON 解析不持有路由锁，socket 写入也沿用锁外写出规则。

选线期间不发布应用就绪状态；若激活写入失败，后台无法假定设备尚未改变角色，会重新确认存活线路。双向线路重新确认时会更新标记，必要时中断旧播报并保留原中断提示，不能承诺无缝播放。已经完成的任务仍保留，执行状态不明的动作不能自动重做。

待发布的亮屏／黑屏意图在路由尚未就绪或发布期间换线时保留，等当前线路确认后再发送，避免把丢弃当作已发布。新激活还会同步当前期望的屏幕状态；同一激活的重复 Hello 不重复发布。角色未确认时丢弃 MIC；显式 Stop 仍可生效，之后重绑不能自行开麦。状态导出只显示协商版本 0／1，不导出随机标记、进程标识或序号。

## 验证范围

自动回归覆盖旧事件和当前软件输出租约、解析中换线、同连接复用、激活乱序／重复／降级、后台重启与退役进程、配置消息归属、能力严格协商、写锁等待中的无代次事件、过期 PCM、失败后存活线路重确认及亮屏意图保留。Java 与 Python 的实际编解码器核对所有原类型的封装／解封、错误标记和边界长度。

上述自动回归使用合成内存数据、loopback socket 和平台替身，没有调用 CC8 麦克风、摄像头或 MiniMax／Dot；实际设备批次另见部署记录。人工拔线、完整待机矩阵、声学插话、电视背景和识别准确率继续分别验收，不关闭 P0-04 或 P0-05。最终 72 小时验收仍排全清单最后。
