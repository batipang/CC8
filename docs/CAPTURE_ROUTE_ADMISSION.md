# 录音线路准入（P0-05）

后台 0.15.48／APK 0.9.45（code82）已部署，运行源码 `ba72bfd`。九项维护检查和独立只读复核通过，见[部署记录](CURRENT_DEPLOYMENT.md#01548code82-录音线路准入)。本改动处理设备发往 Mac 的旧控制与音频包，不能替代物理切换、声学打断或最终长期验收。

## 缺口与行为

0.15.47 已清空停止词解码历史，但保留中的录音在新线路完成重绑前仍能送入完整 MIC 包。使用实际 Bridge／录音前看／端点调用链及确定性停止词后端，旧入口处理 640 个样本并取消新回答。新回归在原生产入口复现一个断言失败，零 fixture 错误。不能只依靠 `rebind_seen`：同一连接对象再次激活时，旧重绑控制与旧 PCM 可能排在队列中。

新设备在初始 `transport_hello` 声明整数 `route_envelope_version=1`。后台每次选中该线路都生成新的 128 位随机值，通过 `transport_activate.route_token` 下发；此值只用于连接代次隔离，不取代 USB 验证、配对认证或 TLS。

设备随后将应用控制、MIC／MIC_PAIRED、RENDER 等包放入 `ROUTE_BOUND=6` 封套。包头的 generation／sequence／frame／nanos 保持，载荷为 16 字节随机值、1 字节原类型（1～5）及原载荷。禁止嵌套，原 PCM 上限 6400 字节和总包体上限 65536 字节保持。`transport_hello`／`transport_pong` 等连接管理消息不封装；设备不向后台发送 `lan_config`。随机值不进入诊断、日志或持久化配置。

Mac 在应用事件分派和音频缓冲前核对当前随机值；错代或协商后未封装的包丢弃。新路由的 MIC 还必须等待当前录音 Start／Rebind 被接受。相同 native capture_id、epoch 和后台生命周期的 capture_start_token 继续沿用，不用更换录音令牌迫使重新开麦。Stop、所有线路丢失和迟到重绑的禁止自启规则保持。

## 设备线程边界

入队时保存原 routeEpoch 和随机值，写出前再次检查原激活，不把旧包改标后转投备用线路。相机请求仍通过原有相机授权和请求归属检查。随机值不能授权相机。

写队列检查不跨越阻塞 socket write 持有 routeLock。若旧包已通过检查才发生切换，它保留旧封套，由 Mac 再次丢弃。录音 worker 在 native read 前保存激活号，若读取跨过切换，整块丢弃并清零；下一次读取前清理自己的成对转换和部分拼包状态。此处不声称测量了 ADC 或硬件内部缓冲的时刻。

## 兼容与验证范围

独立组件复现确认一个接收方向缺口：旧后台 `announcement_begin` 在同一 Link 再次激活后才首次解析时，控制分派取得当前路由号，已清零的代次门槛仍允许它设置播报状态并请求输出。复现编译生产路由／分派方法，接口替身不代表实际设备发声或现场已发生重播；该方向继续作为 P0-05 未完成项。

新端连接旧后台不发送类型 6；旧设备连接新后台保留协议 2 的路径，也丢弃等待重绑期间的 MIC。**只有双方协商新封套时，设备发往 Mac 的包才具备跨激活的隔离保证**；兼容路径不能用来验收该保证。后台向设备的输出仍沿用原回答代次和播放归属机制，本封套没有扩展为双向协议。

离线测试覆盖实际 Java Wire 与 Python 封套双向编解码、分片与边界长度、旧控制、旧 PCM、同一 USB 对象复用、同一对象的新激活、有效新指令、停麦后迟到重绑，以及真实 Channel 的能力协商。Java 测试编译生产队列检查和写出方法，验证排队旧包拒绝、已获准写出仍保留原标记、阻塞写不阻塞换线。实际录音 worker 在受控 native read 屏障下验证 mono／paired 跨激活块丢弃和新块继续。

测试仅使用合成内存数据、loopback socket 和硬件接口替身，没有打开设备麦克风或摄像头，没有调用 MiniMax／Dot。此轮不关闭 P0-04 或 P0-05，电视背景误暂停和一般识别准确率继续保留缺口。最终 72 小时验收仍为全清单最低优先级。
