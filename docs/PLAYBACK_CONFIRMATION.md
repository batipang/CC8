## 超时归属

2026-11-04，自动回归发现等待播报的线程可能在旧暂停解除后才取得会话锁。代次仍然有效时，旧版会取消已恢复的播报，或者取消同代次中随后开始的新暂停。0.14.24 候选在会话锁内同时核对代次和触发超时的暂停状态。状态已经更换时，等待线程重新读取当前暂停及其计时。仍有效的原暂停超时继续按 20 秒取消。

两种真实线程交错在旧版均导致意外推进代次。候选分别验证恢复后的播报继续，以及新暂停等待自己的识别结果。回归使用内存协议接收器，设备仍在运行 0.14.20。该修复针对超时取消竞态，普通音量插话与声学误暂停仍由 P0-04 单独验收。

0.15.37 候选通过现有的可见错误提示告知「插话识别超时，已停止旧播报」。后台仍先取消原播报，再发出新代次的提示，麦克风保持开启。协议和线程回归核对这两个事件的顺序，以及后续新请求能接管状态。实体设备上的 20 秒超时分支待专项验收。

## 回声参考识别失败

已部署的 0.15.41 处理这样一种插话：主语音已返回转录，但回声参考的补充识别失败，插话仍无法确认。旧后台取消原播报。修复后保留本次识别失败回执，拦截未确认的新请求，并按原代次和编号恢复它造成的临时暂停。原播报进行中，失败仅记录在该候选的诊断，不发送会将原播报标记为失败的终态状态。用户已主动停止时，迟到的参考识别失败按取消收尾。主识别失败和暂停的 20 秒总期限沿用现有处理。

后台协议回归使用两路固定 PCM 以及在参考识别中注入的超时。覆盖原播报的暂停和恢复事件，以及用户先停止后收到失败的顺序。该回归没有设备收音或真实云请求，实机声画恢复另行验证。

另经本机证书校验的 HTTPS 夹具，对参考识别分别返回业务超时和连接断开。新旧版每轮均收到一次主识别成功、一次参考识别失败，均未派发新请求。旧版两轮均取消原播报，候选两轮均在原代次发出一次恢复事件，识别请求槽已释放。

已部署的 0.15.42 将相同规则覆盖播报分段之间。0.15.41 在收到上一段的设备播完回执、下一段还未开始时，仍会把参考识别失败发送给原答复的代次。修复后所有未准入的参考识别失败只更新候选自己的诊断，并按原编号释放暂停。线程回归模拟设备播完和参考识别超时的实际顺序，验证同代次恢复和原回执保留。独立 HTTPS 对照覆盖两种故障。 [部署记录](CURRENT_DEPLOYMENT.md#01542code79-部署)

## 连续暂停的设备回执

2026-11-04，0.14.25 候选修复同一代次的连续暂停。旧版只认最近发出的暂停编号。如果后台先发出第二次暂停请求，设备随后按顺序送达第一次暂停和恢复回执，旧版会丢掉第一次回执，导致回声消除使用错误的播放参考。

后台为最多八个待回执编号保存原代次和请求记录。新的设备暂停回执接管后，旧编号失效。恢复必须对应已经请求恢复且收到暂停回执的编号，设备时间不能倒退。回执只更新参考时间线和原请求诊断，当前暂停仍由自己的识别结果处理。取消、会话和通道重置清理待回执。

回归通过后台正常事件入口驱动实际 PCM 参考时间线。旧版在第一次暂停回执已到或仍在途两种顺序下，都会错放两次暂停间的参考。候选验证真实停播区间的参考为零，恢复区间保留原 PCM，并覆盖未请求恢复、倒退、重放、待回执上限和新回执接管。数据由测试构造，声学与实体设备验收仍按 P0-04 记录。

## 播放器创建与插话暂停的顺序

后台 0.14.35 候选处理播报开头的竞态。原先 Mac 在发送 `play_begin` 前就标记本地播报已开始，收音线程可能先发出 `playback_pause`。CC8 此时还没有对应播放器，会忽略暂停；Mac 却已经设置了临时暂停状态。

候选保留开始发送时的播报归属供取消和切换使用，并在 `play_begin` 完整发出后才允许临时暂停。此前收到的音频仍进入原有识别流程。发布状态与暂停准入使用既有锁顺序，写管道不持有播报发布锁。取消后不会继续发送旧播报的 PCM。

主机回归通过两个线程控制发出 `play_begin` 前、发出后至首包 PCM 前的交错，在旧代码复现一次误暂停。候选确认线路顺序为开始、暂停、恢复、结束。该检查使用固定 PCM 和本地传输替身，候选未部署，实际插话与声画时延仍按 P0-04 实机验证。

## 排队中的播报事件与会话代次

后台 0.14.37 候选在写锁内重新检查显式携带会话代次的控制事件。旧版只在生成协议包前检查，已经通过检查的 `play_begin` 或 `caption_timing` 可以在取消后才写出，甚至写到刚切换的连接。播放 PCM 已在写锁内检查，此次把控制事件补齐。工作区和设置等未指定代次的消息沿用原行为。

线程回归分别在生成协议包时暂停发送和在写锁前排队，覆盖同通道取消、USB 切到 Wi-Fi，以及取消已经推进代次但两条消息仍在等写锁。旧版三处断言失败，候选仅发送当前播报或取消事件。软件候选未部署，实体切换仍独立验收。

## 播报结束回执的帧数核对

后台 0.14.39 候选在提交 `play_end` 时记录已发出的语音帧数，只有对应会话与播报句的 `play_done` 才能确认完成。设备若报告了播放头帧数，则至少要达到本句语音帧数。暂停恢复补的静音可使播放头超过语音帧数，仍接受该回执。旧设备省略播放头帧数时继续使用已有兼容规则。

回执在本轮结束消息的发送调用返回前到达也可处理。确认后即消费这次等待状态，重复回执不会改写结束时间或重算回声尾段。回归使用固定 PCM，复现提前回执、短播回执和重复回执，候选只接受有效回执一次。实际扬声器出声和实体切换仍按实机矩阵验证。

## 设备暂停与恢复回执

APK 0.9.20 候选在 Android `AudioTrack.pause()` 或 `play()` 成功返回后，才取设备单调时钟并发送对应回执。初始化期间的暂停先记录为待执行，在第一段 PCM 写入前应用。若在初始化前收到同一暂停的恢复指令，则撤回，两个回执都省略。播放器调用失败时，终止本次播放并发送已有的播放错误事件。

设备时间戳记录 Android 调用返回。Mac 的 `pause_roundtrip_ms` 仍记录从发出暂停请求到收到回执的单端耗时。实际可听停播和人声起点到停播时延仍需声学测量。Java 回归以固定的 AudioTrack 替身调用实际播放器控制方法，覆盖初始化、撤回、重复、失败与取消。实体设备回归留到长稳观察结束。

## 自动记录插话触发至设备暂停时延

APK 0.9.22 候选在握手中声明已执行暂停回执。后台 0.14.43 使用 CC8 的同一单调时钟，从满足暂停门槛的录音帧起点估算值算到 `AudioTrack.pause()` 成功返回，记录为 `device_pause_from_trigger_ms`。报告保留逐请求结果，只有被准入的语音回合进入该指标的样本数、P50 和 P95。旧版、缺失回执或无效时间差没有样本。Mac 回执往返耗时独立保留。

后台 0.14.64 起，同一暂停回执可另报 `device_pause_from_vad_onset_ms`。起点使用这段话被 VAD 接纳前、连续判为有声的一段录音的首帧，结束点仍是设备应用暂停。捕获时钟不连续或首帧不可确认时，保留原触发指标并省略新指标。批次分别统计两种样本，旧后台继续按原字段复核。录音帧时间仍是设备侧估算，有声判定也会受到 AEC 和噪声影响，真人起声到扬声器停声另行实测。

录音帧起点由采样位置推算，读停顿或采样时钟漂移可能影响估算。人声实际起点与扬声器实际停止出声仍由声学测试确认。离线回归覆盖延后触发、识别队列交接后才到达的回执、旧设备及无效时差。

## 暂停时的字幕与嘴型

APK 0.9.28 候选将每次界面刷新所用的嘴型、波形和字幕进度绑定到同一个播放器和播放头读数。Android 应用暂停后冻结该位置，嘴型归零。迟到的字词时序可以更新播放器，但在恢复前不改变已冻结的高亮和进度。恢复播放时回到当前播放头，取消时丢弃旧画面状态。

离线回归以实际 Java 播放控制和时序计算核对暂停与刷新并发、暂停期间播放头变化和迟到时序、恢复及取消。扬声器停声和实体屏幕刷新之间的时间仍待实测。

## 播放界面回调的归属

APK 0.9.30 候选在播放器提交界面更新时检查播放器归属。主线程实际应用字幕与播放状态前，再核对更新是否仍然有效。取消或切换会使旧更新失效，同一播放器较早的暂停也不能覆盖后来恢复的状态。自然播完的最后一帧可以在主线程稍后显示。

离线回归将实际播放器发布逻辑和 Activity 回调放入可控的 Java 队列，覆盖旧播放器迟到、暂停与恢复乱序、自然播完和界面进入后台。实体设备待长稳观察结束后验证。
