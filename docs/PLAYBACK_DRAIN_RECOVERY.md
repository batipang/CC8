# 没有显式恢复时的短尾排空

APK 0.9.38／code75 源码候选。后台保持 0.14.87、协议保持 2，尚未安装此 APK。它修复现有排空模型中一种未覆盖路径，不将上一轮实机超时直接判为该原因。

## 已有证据

0.14.87／code74 的报告 `device-20261105T142716Z-59ad5e9b.json` 在预备播报失败，收尾关麦。后台记录 first PCM、设备 RENDER 和起播回执，随后等待播放完成回执超时；这轮尚未启动收音或已知插话观察。完整范围见 [当前部署](CURRENT_DEPLOYMENT.md)。

同仓库的 Java 流式轨道模型设定：尚余 1857 帧语音、原生缓冲为 4096 帧，缓冲重新填满才恢复推进。现有 `PlaybackDrain` 在 `resumeSerial=1` 时补 2239 帧零后完成；同一模型的 `resumeSerial=0` 会等待 3000 毫秒并抛出异常，始终没有补零。这是受控模型的数值，模型播放头 20,992 不是此次设备测量。

[Android 的 AudioTrack.play 文档](https://developer.android.com/reference/android/media/AudioTrack#play()) 说明，流式轨道欠载后也可能需要重新填至设备最低缓冲量，并不限于显式停止／恢复。文档支持检查这一软件路径，不能证明 CC8 这次超时的物理原因。

## 候选行为

排空时仍先比较真实播放头与语音帧终点。播放头继续推进则不补零；尚未到达终点且连续 100 毫秒不推进，才允许沿用静音补充路径。显式恢复继续即时使用原路径。累计补充仍不超过一个已核对的原生缓冲，缓冲范围仍为 1～32,000 帧。

补零只增加独立的 padding 计数，不改变语音帧数、RENDER、字幕或嘴型终点；不能用“已写入缓冲”替代“播放头已到达”。永久不动的轨道依然在原截止时间失败；取消和失去归属立即退出，等待显式暂停的时间仍从截止预算中扣除。没有提高主机 ACK 超时或伪造播放回执。

## 验证

Java 回归执行真实 `PlaybackDrain`／`PcmPump`，覆盖不经暂停的可恢复欠载、普通推进、永久停滞、短写、取消、暂停等待、重复恢复、非法缓冲及已播完终点。补零全部检查为零采样，语音计数不被增加。旧代码的同一新恢复用例应失败，才计作回归能检出缺口。
